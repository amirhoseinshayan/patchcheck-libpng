# libpng `pnginfo` — independent reference behaviour

Status: written by the group from the PNG specification and the documented
behaviour of libpng's `png_set_PLTE` / `png_get_PLTE` interface. Expected outputs
are derived from this document, never from running any version of the program.
The inputs and oracle JSON files are generated by `tools/gen_libpng_corpus.py`.

Target program: `pnginfo`, a minimal C reader built on libpng (the real
library). It opens a PNG, decodes it, and for palette images re-encodes it
through the public `png_set_PLTE` API with a 256-entry palette, then copies the
reported palette into a buffer whose size is the correct maximum for the bit
depth (`1 << bit_depth`). The real defect under test is **CVE-2015-8126** and its
incomplete fix **CVE-2015-8472**: `png_set_PLTE`/`png_get_PLTE` did not clamp the
palette size to the bit depth, so a small-bit-depth image can carry up to 256
palette entries.

## Invocation

`pnginfo FILE`. On success the program prints one line to stdout and exits 0:

```
OK <width> <height> <bit_depth> <color_type> <num_palette>
```

`color_type` is 3 for a palette image. `num_palette` is the palette size the
re-encode reports (`png_get_PLTE`). For an 8-bit palette image the PNG
specification allows at most `1 << 8 = 256` entries, so the 256-entry re-encode
is accepted and reported unchanged.

## Rendering (valid inputs)

All test images are a single 1×1 palette pixel with a global PLTE chunk.

1. An 8-bit palette image with 128 entries is valid; the 256-entry re-encode is
   still within the 8-bit maximum and is reported as 256.
2. An 8-bit palette image with 256 entries is the exact boundary (maximum);
   it is valid and reported unchanged.

stdout is exactly `OK 1 1 8 3 256\n`, stderr is empty and the exit code is 0.

## Errors

On these conditions `pnginfo` prints exactly `png error` to stderr and exits 1;
stdout is empty:

| Condition | stderr |
|---|---|
| A palette image has no PLTE chunk | `png error\n` |
| IHDR declares an invalid bit-depth/colour-type combination (bit depth 16 with a palette) | `png error\n` |

## Security property

No input may cause an out-of-bounds memory access. For a palette image, the
number of palette entries accepted by `png_set_PLTE` must not exceed
`1 << bit_depth`. When `pnginfo` re-encodes a small-bit-depth image with a
256-entry palette, a conforming libpng must reject it:

| Condition | correct behaviour |
|---|---|
| A 1-bit (or 2-bit) palette image re-encoded with a 256-entry palette | `png_set_PLTE` rejects the oversized palette; `png error\n`, exit 1 |

The vulnerable build accepts all 256 entries and reports `num_palette = 256`.
When the application then copies that many entries into a buffer sized for the
correct maximum (`1 << bit_depth`), the copy writes past the buffer: a
heap-buffer-overflow WRITE (AddressSanitizer in the instrumented build, and
`FORTIFY_SOURCE` `*** buffer overflow detected ***` or a glibc heap-corruption
diagnostic in the release build).
